## Краткий обзор

В рамках **Части 1** реализован драйвер сетевой карты Intel 82540EM (e1000)
для учебной операционной системы JOS.

Что умеет драйвер:
- Находить карту на шине PCI и настраивать её через PCI Config Space.
- Отображать регистры карты в виртуальное адресное пространство (MMIO).
- Читать MAC-адрес из EEPROM.
- Отправлять сырые Ethernet-фреймы.
- Принимать сырые Ethernet-фреймы (в режиме опроса, без прерываний).

**Часть 2** (сетевой стек: ARP, ICMP, UDP, TCP, HTTP) строится поверх
трёх функций, объявленных в `fs/e1000.h`.

## Архитектура JOS и место драйвера

JOS — микроядерная ОС: каждый системный сервис живёт в отдельном
пользовательском процессе.

```
┌─────────────────────────────────────────────┐
│ Ядро (kern/)                                │
│  • управление памятью (pmap.c)              │
│  • планировщик (sched.c)                    │
│  • обработка прерываний (trap.c)            │
│  • системные вызовы (syscall.c)             │
└──────────────────┬──────────────────────────┘
                   │ системные вызовы
┌──────────────────▼──────────────────────────┐
│ FS-сервер (fs/serv.c)  — userspace-процесс  │
│                                             │
│  pci_init()   — сканирование шины PCI       │
│  nvme_init()  — драйвер NVMe SSD            │
│  e1000_init() — ЭТОТ драйвер                │
│                                             │
│  serve()      — цикл обработки IPC-запросов │
└─────────────────────────────────────────────┘
```

FS-сервер запускается с привилегиями IOPL=3 (доступ к портам ввода-вывода)
и имеет право вызывать `sys_map_physical_region()` для отображения
физической памяти устройства в своё виртуальное адресное пространство.

Это тот же процесс, где уже живёт драйвер NVMe (`fs/nvme.c`).
e1000-драйвер написан по тому же шаблону.

## Выбор сетевой карты

Выбрана **Intel 82540EM** (модель QEMU — `e1000`), потому что:
- Это сетевая карта по умолчанию в QEMU для машины типа q35.
- JOS уже использует q35 (`-M q35` в GNUmakefile), изменений не требуется.
- Подробная спецификация открыта: "Intel 82540EM Gigabit Ethernet Controller
  Software Developer Manual" (Intel, document 317453).

PCI-идентификаторы карты:
| Поле        | Значение     |
|-------------|-------------|
| Vendor ID   | `0x8086` (Intel) |
| Device ID   | `0x100E` (82540EM) |
| Class       | `0x02` (Network Controller) |
| Subclass    | `0x00` (Ethernet) |

## Как работает PCI

PCI (Peripheral Component Interconnect) — стандарт подключения устройств
к материнской плате. Каждое устройство однозначно идентифицируется тройкой
**(bus, device, function)** и имеет **конфигурационное пространство** — 256
байт специальных регистров:

```
Offset 0x00  Vendor ID      (кто сделал карту: 0x8086 = Intel)
Offset 0x02  Device ID      (модель карты: 0x100E = 82540EM)
Offset 0x04  Command        (управление: bit 2 = Bus Mastering)
Offset 0x10  BAR0           (Base Address Register: адрес MMIO-регистров)
Offset 0x3C  Interrupt Line (номер IRQ)
```

**BAR (Base Address Register)** — это физический адрес, по которому
видны регистры устройства в физической памяти процессора.

В JOS доступ к PCI Config Space реализован через **ECAM**
(Enhanced Configuration Access Mechanism) — карта сопоставляет
конфигурационное пространство с физической памятью, начиная с
адреса `0xB0000000`. Соответствующий код в `fs/pci.c`.

**Bus Mastering** — флаг, который разрешает устройству самостоятельно
писать в оперативную память (DMA). Без него отправка/приём пакетов
не работает. Включается установкой бита 2 в регистре Command.

## Что такое MMIO и DMA

### MMIO (Memory-Mapped I/O)

Регистры устройства (управляющие биты, статусные слова) отображены в
физическое адресное пространство процессора. Чтение/запись обычными
командами `mov` по специальному адресу читает/пишет именно аппаратный
регистр, а не RAM.

В драйвере функция `e1000_map()` вызывает `sys_map_physical_region()`,
чтобы виртуальный адрес `0x7030000000` стал окном в BAR0 карты.
После этого:
```c
*(volatile uint32_t *)(nic.mmio + E1000_CTRL) = E1000_CTRL_RST;
```
— это аппаратный сброс NIC, а не запись в оперативную память.

Флаг `PROT_CD` (Cache Disable) критичен: без него процессор может
закешировать чтение регистра, и статусный бит будет виден устаревшим.

### DMA (Direct Memory Access)

Когда драйвер хочет отправить пакет, он **не** копирует данные
в память карты байт за байтом. Вместо этого:
1. Драйвер кладёт данные в **буфер в оперативной памяти** и
   сообщает карте **физический адрес** этого буфера.
2. Карта самостоятельно считывает данные из RAM через шину PCI и
   передаёт их по сети (TX DMA).
3. Аналогично для приёма: карта пишет входящий пакет прямо в RAM
   по адресу, который ей заранее дал драйвер (RX DMA).

Проблема: ОС работает с **виртуальными** адресами, а карте нужен
**физический** адрес. Функция `get_phys_addr(va)` читает пользовательскую
таблицу страниц (`uvpt`) и возвращает физический адрес для заданного
виртуального.

## Структура драйвера e1000

### Кольца дескрипторов

Связь между процессором и NIC осуществляется через два **кольцевых
буфера дескрипторов** в оперативной памяти.

**TX-кольцо** (отправка):

```
Дескриптор 0: [физ.адрес буфера | длина | флаги | статус DD]
Дескриптор 1: [физ.адрес буфера | длина | флаги | статус DD]
...
Дескриптор 15:
```

Каждый дескриптор — 16 байт. Драйвер заполняет один дескриптор и
сдвигает `TDT` (Tail) — это сигнал карте начать отправку. Когда карта
заканчивает, она устанавливает бит `DD` (Descriptor Done) в статусе.

```
          CPU записывает дескриптор             NIC читает дескриптор
                    ↓                                    ↓
[0][1][2] ... [tail] ...          [head] ... [tail]
               ↑                   ↑
           драйвер              NIC (hardware)
```

**RX-кольцо** (приём) работает симметрично: драйвер заранее заполняет
все дескрипторы физическими адресами буферов (куда NIC будет писать
входящие пакеты) и устанавливает `RDT`. NIC заполняет буферы и
ставит `DD`. Драйвер читает `DD`, копирует данные и отдаёт дескриптор
обратно NIC, сдвигая `RDT`.

### Расположение памяти

```
Виртуальный адрес        Назначение
─────────────────────────────────────────────────────────────
0x7000000000             ECAM (PCI Config Space, ~4 MB)
0x7010000000             NVMe MMIO-регистры (BAR0, 32 KB)
0x7020000000             NVMe DMA-очереди (16 страниц)
0x7030000000             e1000 MMIO-регистры (BAR0, 128 KB)
0x7040000000             e1000 DMA (18 страниц):
  +0x0000                  TX-дескрипторы  (16 × 16 байт)
  +0x1000                  RX-дескрипторы  (16 × 16 байт)
  +0x2000                  TX-буферы пакетов (16 × 2048 байт)
  +0xA000                  RX-буферы пакетов (16 × 2048 байт)
```

### Последовательность инициализации (`e1000_init`)

```
1. find_pci_dev(0x02, 0x00)       — найти Ethernet-контроллер на PCI
2. pci_enable_busmaster()         — разрешить карте DMA
3. e1000_map()                    — отобразить BAR0 в VA-пространство
4. CTRL.RST = 1, ждать сброса     — привести все регистры к умолчаниям
5. IMC = 0xFFFFFFFF               — отключить прерывания (работаем в polling)
6. e1000_mac_read()               — прочитать MAC из EEPROM через EERD
7. e1000_alloc_dma()              — выделить 18 страниц DMA-памяти
8. e1000_tx_init()                — инициализировать TX-кольцо
9. e1000_rx_init()                — инициализировать RX-кольцо
```

### Отправка пакета (`e1000_send`)

```c
int e1000_send(const void *buf, size_t len);
```

1. Берём слот `tx_tail` из TX-кольца.
2. Проверяем, что слот свободен: либо никогда не использовался (`cmd == 0`),
   либо NIC поставил `DD` (завершил предыдущую отправку).
3. Копируем данные в TX-буфер[tail].
4. Заполняем дескриптор: `addr` = физадрес буфера, `length`, `cmd = RS|EOP|IFCS`.
5. Записываем `TDT = (tail + 1) % 16` — доорбелл для NIC.
6. Возвращаем `0` (успех) или `-1` (кольцо заполнено).

### Приём пакета (`e1000_recv`)

```c
int e1000_recv(void *buf, size_t *len);
```

1. Проверяем дескриптор `(rx_tail + 1) % 16`: если `DD == 0` — нет пакета.
2. Копируем данные из RX-буфера[next] в `buf`.
3. Сбрасываем `status = 0`.
4. Записываем `RDT = next` — возвращаем слот NIC.
5. Возвращаем `0` (пакет получен) или `-1` (нет пакета).

## Запуск и тестирование

### Вариант 1: User-mode сеть (без root, по умолчанию)

```bash
make qemu-nox
```

QEMU создаёт внутренний NAT. Пакеты, исходящие от JOS, **не видны** на
хосте, но можно тестировать через `hostfwd`. В консоли JOS при старте
будет:

```
e1000: found at PCI bus 0 dev 3 func 0 (vendor=0x8086 device=0x100e)
e1000: MAC = 52:54:00:12:34:56
e1000: init done  link=up  STATUS=0x...
e1000_test: test frame sent (64 bytes, dst=broadcast)
e1000_test: no frame received (expected without inbound host traffic)
```

### Вариант 2: TAP (наблюдение через Wireshark/tshark)

**Шаг 1** — создать TAP-устройство (один раз):

```bash
make tap-setup TAP_NAME=tap0
```

Или вручную:

```bash
sudo ip tuntap add tap0 mode tap user $(whoami)
sudo ip link set tap0 up
sudo ip addr add 192.168.56.1/24 dev tap0
```

**Шаг 2** — запустить QEMU с TAP:

```bash
make qemu-nox QEMUNET=tap TAP_NAME=tap0
```

**Шаг 3** — наблюдать трафик (в отдельном терминале):

```bash
sudo tshark -i tap0
# или
sudo wireshark &  # выбрать tap0
```

Вы увидите исходящий широковещательный Ethernet-фрейм от JOS.

**Шаг 4** — отправить пакет в JOS:

```bash
# В третьем терминале:
echo 'Hello JOS' | nc -u 192.168.56.101 10001
```

> Адрес `192.168.56.101` — гостевой IP JOS, `10001` — порт.
> JOS пока не реализует IP (это Часть 2), но на уровне Ethernet
> фрейм будет виден в RX-кольце и напечатан hex-дампом.

**Удаление TAP**:

```bash
sudo ip link delete tap0
```

### Что проверить в первую очередь

| Проверка | Ожидаемый результат |
|---|---|
| Строка "e1000: found at PCI..." | NIC найден на шине PCI |
| Строка "e1000: MAC = 52:54:00:12:34:56" | EEPROM читается корректно |
| Строка "link=up" | QEMU поднял виртуальный линк |
| Фрейм в tshark | TX-путь работает |
| Hex-дамп принятого пакета | RX-путь работает |

## Интерфейс для Части 2

Код сетевого стека (ARP, ICMP, UDP, TCP, HTTP) строится поверх трёх
функций, объявленных в `fs/e1000.h`:

```c
// Инициализация карты (вызывается в fs/serv.c, один раз при старте)
void e1000_init(void);

// Отправить сырой Ethernet-фрейм.
// buf: данные (включая Ethernet-заголовок), len: длина в байтах.
// Возвращает 0 при успехе, -1 если TX-кольцо заполнено (повторить позже).
int e1000_send(const void *buf, size_t len);

// Принять сырой Ethernet-фрейм (неблокирующий опрос).
// Если фрейм есть: копирует в buf, записывает длину в *len, возвращает 0.
// Если нет: возвращает -1.
int e1000_recv(void *buf, size_t *len);

// Получить MAC-адрес NIC (6 байт).
void e1000_get_mac(uint8_t mac[6]);
```

Типичный стек Части 2:

```
e1000_send / e1000_recv     ← сырые Ethernet-фреймы
        ↓             ↑
    Ethernet          |     (fs/net_eth.c: разбор заголовка)
        ↓             ↑
  ARP / IP разбор     |     (fs/net_arp.c, fs/net_ip.c)
        ↓             ↑
  ICMP / UDP / TCP    |     (fs/net_icmp.c, fs/net_udp.c, fs/net_tcp.c)
        ↓             ↑
    HTTP-сервер       |     (fs/net_http.c)
```

Замечания для реализатора Части 2:
- MAC-адрес NIC зафиксирован как `52:54:00:12:34:56` (задаётся в GNUmakefile)
  — можно захардкодить в ARP-таблице.
- IP-адрес JOS по умолчанию: `192.168.56.101` (согласован с `hostfwd` в GNUmakefile).
- `e1000_recv` возвращает `-1` немедленно, если нет пакета. Вызывай в цикле
  или реализуй прерывание (IRQ) поверх существующих дескрипторов.
